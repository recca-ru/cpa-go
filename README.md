# Go-клиент CPA-API Recca

`go.recca.ru/cpa` — клиент машинной двери `/federation/v1/cpa/*`: партнёры,
каталог офферов, ссылки, клики, конверсии, выплаты и статистика вашей сети в
Recca. Нужен Go 1.24 или новее.

Лицензия проприетарная: код предназначен клиентам Recca для интеграции с API
по договору — см. `LICENSE`. ⚠ Поэтому pkg.go.dev документацию модуля не
показывает; она в этом README и в `go doc go.recca.ru/cpa`.

Ключ арендатора живёт на вашем **сервере** и в браузер не попадает: один ключ
адресует любого партнёра сети, а разграничивать людей — ваша работа.

## Квикстарт

```go
client, err := cpa.New(os.Getenv("RECCA_CPA_KEY"), &cpa.ClientOptions{Environment: cpa.Sandbox})
if err != nil { log.Fatal(err) }
conv, _, err := client.Conversions.Create(context.Background(), cpa.CreateConversionParams{
	ClickID: clickID, ExternalID: "order-0751", Status: "approved", SumRUB: cpa.RUBPtr(10000)})
switch {
case errors.Is(err, cpa.ErrWindowExpired): log.Print("окно атрибуции истекло — не повторять")
case err != nil: log.Printf("не принято: %v", err) // в тексте ошибки — код и request_id
default: log.Printf("принято: %s, выплата %s ₽", conv.Status, conv.PayoutRUB)
}
```

⚠ Нулевое значение `Environment` — это **боевая** сеть. Пока вы пробуете, пишите
`Environment: cpa.Sandbox` явно.

Полная программа — [`examples/quickstart`](examples/quickstart/main.go). Примеры
на каждый сервис исполняются `go test -run Example ./...` и лежат в
[`example_services_test.go`](example_services_test.go).

Ветвитесь по **коду** ошибки через `errors.Is(err, cpa.ErrXxx)`, а не по тексту:
текст меняется без предупреждения. Отказ, выданный клиентом до сети
(`errors.Is(err, cpa.ErrValidation)`), называет поле и в журналах Recca его нет.
Сообщая о проблеме, называйте `request_id` из ответа или ошибки.

Бюджет запросов в минуту для вашего ключа отдаёт `Self.Get`
(`SelfInfo.RateLimitPerMin`) — берите его оттуда, а не из документации.

## Методы

Восемнадцать дверей контракта — двадцать методов: у оффера две проекции, и они
разведены **именами методов**, а не параметром. Партнёрская проекция не несёт
ставок рекламодателя и наоборот; параметр можно забыть, имя метода — нет.

Скоуп — право ключа, которое спрашивает дверь; без него ответ
`403 INSUFFICIENT_SCOPE`. «Повтор» — повторяет ли клиент запрос сам при сетевом
сбое или временном отказе. Чтения повторяются всегда; запись — только если у
операции есть ключ идемпотентности.

| Метод | Дверь | Скоуп | Повтор |
|---|---|---|---|
| `Self.Get` | `GET /cpa/self` | `cpa:self:read` | да |
| `Self.SetWebhook` | `PUT /cpa/self/webhook` | `cpa:self:write` | **нет** |
| `Partners.Upsert` | `POST /cpa/partners` | `cpa:partners:write` | да |
| `Partners.List` | `GET /cpa/partners` | `cpa:partners:read` | да |
| `Partners.Get` | `GET /cpa/partners/{external_id}` | `cpa:partners:read` | да |
| `Partners.Balance` | `GET /cpa/partners/{external_id}/balance` | `cpa:partners:read` | да |
| `Offers.ListForPartner` | `GET /cpa/offers?view=partner` | `cpa:offers:read` | да |
| `Offers.ListForAdvertiser` | `GET /cpa/offers?view=advertiser` | `cpa:offers:read` | да |
| `Offers.GetForPartner` | `GET /cpa/offers/{id}?view=partner` | `cpa:offers:read` | да |
| `Offers.GetForAdvertiser` | `GET /cpa/offers/{id}?view=advertiser` | `cpa:offers:read` | да |
| `Offers.Creatives` | `GET /cpa/offers/{id}/creatives` | `cpa:offers:read` | да |
| `Links.Create` | `POST /cpa/links` | `cpa:links:write` | да |
| `Clicks.Create` | `POST /cpa/clicks` | `cpa:clicks:write` | **нет** |
| `Conversions.Create` | `POST /cpa/conversions` | `cpa:conversions:write` | да |
| `Conversions.List` | `GET /cpa/conversions` | `cpa:conversions:read` | да |
| `Conversions.Get` | `GET /cpa/conversions/{external_id}` | `cpa:conversions:read` | да |
| `Conversions.Cancel` | `POST /cpa/conversions/{external_id}/cancel` | `cpa:conversions:reverse` | да |
| `Payouts.Create` | `POST /cpa/payouts` | `cpa:payouts:write` | да |
| `Payouts.List` | `GET /cpa/payouts` | `cpa:payouts:read` | да |
| `Statistics.Get` | `GET /cpa/statistics` | `cpa:stats:read` | да |

Операторских методов нет и не будет: офферы, условия и отметку «выплачено»
заводит оператор в кабинете Recca.

Для запроса, которого нет среди методов, есть `client.Do` — тот же конверт,
разбор ошибок и политика повтора.

## Ловушки

Всё ниже — поведение двери, сверенное с её кодом, а не с описанием.

**`Self.SetWebhook` не повторяется, секрет показывается один раз.** Секрет
подписи приходит в ответе при **первой** установке адреса и при ротации — и
больше никогда. Повтор после потерянного ответа вернул бы успех без секрета,
то есть потерял бы его молча, поэтому клиент такой запрос сам не повторяет.
Не получили ответа — вызовите снова с `RotateSecret: true` и сохраните новый
секрет. Смена адреса без ротации секрета не показывает.

**`Partners.Upsert`: роль и ставку агента меняет оператор.** На уже заведённом
партнёре дверь меняет только ваши поля — участие (`PartnerState`) и рекрутёра.

У рекрутёра три состояния: пустой `RecruiterExternalID` — не меняем; непустой —
прикрепить или сменить; `DetachRecruiter: true` — открепить (в теле уходит
`null`). Открепление действует вперёд: уже начисленные ноги агента остаются,
новые конверсии партнёра приходят без них. Оба поля сразу — отказ до сети.

| Что прислали на повторе | Ответ |
|---|---|
| другую `Role` | `400 INVALID_INPUT`, поле `role` |
| другой `AgentPercent` у действующего агента | `400 INVALID_INPUT`, поле `agent_percent` |

Практическое следствие: **синхронизация, которая шлёт роль со своей стороны,
начнёт падать на партнёре, которого оператор перевёл в агенты**, — и будет
падать на нём каждую ночь. Сверяйте роль с `Partners.Get` либо не пересылайте
её для уже заведённых. У приостановленного партнёра роли нет, и с ним ничего не
сверяется — поэтому отказы начнутся не в момент перевода, а когда его вернут в
строй.

**Оффер: две проекции — два метода.** `ListForAdvertiser` и `GetForAdvertiser`
отдают выручку рекламодателя; `ListForPartner` и `GetForPartner` — ставку
партнёра. Каталог рекламодателя требует рекламодателя:
`ListForAdvertiser(ctx, advertiserID, params)`, без него отказ до сети.

**`Clicks.Create` не повторяется.** Повтор — это второй переход и лишний расход
капа оффера. Если ваш фронт может продублировать вызов, присылайте свой
`ClientClickID`: с ним повтор вернёт тот же клик. Отбитый переход
(`Status == cpa.ClickTrafficback`) — **не ошибка**: запрос верный, но кап
исчерпан или гео не подходит; тогда `ClickID` и `RedirectURL` — `nil`, причина
в `Reason`.

**И 201, и 200 — успех.** Конверсия, партнёр, ссылка, выплата и клик с
`ClientClickID` на повторе отвечают `200` с тем же объектом, на создании — `201`.
Клиент, считающий успехом только `201`, сломается на первом же повторе.

**Выплата: ключ — партнёр и период, сумма сверяется.** `PayoutParams`
собирается только через `cpa.NewPayoutParams(partner, amount, from, to)`.
Повтор за тот же период с той же суммой возвращает ту же заявку; с **другой**
суммой — `409 IDEMPOTENT_MISMATCH` (`cpa.ErrIdempotentMismatch`), а не вторая
заявка. Отметку «выплачено» ставит оператор.

**Конверсия адресуется тройкой «сеть + номер заказа + цель».** Номер заказа
общий для всей сети. Без цели (`Goal == nil`) и с пустой целью дверь берёт цель
по умолчанию `"1"`; другую цель называют явно — в `Get` и `Cancel` так же, как
в `Create`.

**Повтор и переход — разные вещи.** Повтор — это тот же номер заказа с запросом,
который **уже исполнен**: тот же статус либо статус, до которого конверсия уже
дошла. На повторе сумма сверяется: та же — успех с `200`; другая —
`409 IDEMPOTENT_MISMATCH`; «не передали» (`nil`) и `0` — разные суммы. Смена
статуса, которой ещё не было, — не повтор, а **переход**, и сумму на нём
передавать МОЖНО: заказ, принятый в ожидании (`pending`) без суммы или с
предварительной, подтверждается вызовом `Create` со статусом `approved` и
итоговой суммой. Недопустимый переход — `409 ILLEGAL_TRANSITION`: из отменённой
конверсии никуда, а подтверждённую нельзя вернуть в ожидание.

Присланный `approved` дверь заводит в холд (`hold`), а по его истечении
конверсия становится доступной к выплате (`approved`). **Тот же `approved`,
досланный после холда, — тоже повтор**: `200`, та же конверсия, деньги не
двигаются. Поздний дубль постбэка отдельной обработки не требует. (До контракта
2026-09-24 дверь отвечала на него `409 ILLEGAL_TRANSITION`.)

**Префикс `recca:` в номере заказа занят платформой.** Создать конверсию с ним
нельзя — без учёта регистра и пробелов по краям; клиент отказывает до сети.

**Отмена конверсии терминальна, а её повтор безопасен.** Отменённую конверсию
нельзя снова подтвердить: `Create` на ней ответит `409 ILLEGAL_TRANSITION`.
Повтор самой отмены ничего не меняет и отвечает той же конверсией, поэтому
`Cancel` повторяется при сбое сам.

**Статистика считается по времени события.** День конверсии — `occurred_at`, а
если вы его не прислали, — время приёма. Досланная пачкой вчерашняя конверсия
попадает во вчерашний день.

**Поля, которые дверь присылает `null`, — указатели.** `HoldUntil`,
`OccurredAt`, `AgentLeg`, `PaidAt` и подобные законно бывают `nil`.
Разыменовывать их без проверки значит однажды уронить свой сервер на законном
ответе.

## Граница моков: `cpatest`

`cpatest.NewServer(t)` — стенд на `httptest`, который отвечает на все
восемнадцать дверей конвертом контракта. Для примеров и `main` без `*testing.T`
есть `cpatest.Start()` (закрывать самому).

**Стенд доказывает:** что ваш код собирает верные запросы (`Requests()` отдаёт
увиденное — метод, путь, строку запроса, тело), разбирает верные ответы и
проходит ветки ошибок.

**Стенд НЕ доказывает** поведение платформы: тройку ставок, срок холда,
идемпотентность живой двери, право партнёра работать, капы и гео. Числа в его
ответах — фикстуры. Это предмет песочницы. Из логики в стенде есть ровно две
вещи — повтор конверсии (та же тройка → тот же объект и `200`) и повтор заявки
на выплату (другая сумма → `409`), — чтобы набор `Conformance` можно было
прогнать и против стенда.

Два режима заготовленного отказа:

| Режим | Что делает | Когда |
|---|---|---|
| `PrepareError(code)` | отказ ровно на ОДИН следующий запрос | клиент без повторов — например, из `Server.Client(t)` |
| `HoldError(code)` + `ClearError()` | отказ на КАЖДОМ запросе до снятия | ваш собственный клиент с повторами |

⚠ Одноразовый отказ на **повторяемом** коде (`500`, `503`, `429`) съедает
политика повтора клиента: первая попытка получает отказ, вторая — обычный ответ,
и тест ветки отказа зеленеет по неправильной причине. Работаете своим клиентом
с повторами — берите `HoldError`.

### `cpatest.Conformance`

Приёмочный набор: `cpatest.Conformance(t, client, opts)`. Проходит четыре
цепочки — самопроверку, каталог, вертикаль «партнёр → ссылка → клик → конверсия
→ повтор конверсии», выплату — и сверяет подписи постбэка и вебхука.

⚠⚠ **Работает только против песочницы и стенда.** До первого запроса набор
сверяет базовый адрес клиента: разрешены песочница и петля (`127.0.0.1`,
`localhost`, `[::1]`); на любом другом адресе — отказ и **ни одного запроса**.
Флага «разрешить прод» нет. Причина: набор создаёт данные, а нулевое
`Environment` — боевое; забытое `Environment: cpa.Sandbox` при боевом ключе
создавало бы в живой сети партнёра, конверсию и заявку на выплату при каждом
прогоне вашего CI.

Второй ремень — ответ самого сервера: `GET /cpa/self` называет среду
(`SelfInfo.Environment`), и если это не `sandbox`, набор останавливается до
первой записи. Адрес можно направить не туда прокси или DNS, ответ двери о
себе — нет.

Что набор создаёт в песочнице за прогон: партнёра (по умолчанию
`conformance-webmaster`), ссылку, клик, конверсию со статусом `approved` и
суммой заказа 2500 ₽ под номером `conformance-order-<метка>` и — если баланс
позволяет — заявку на выплату в размере порога выплаты партнёра. Номера заказа и
ключ клика уникальны на прогон.

**Цепочка выплат проверяет согласованность баланса и двери заявок.** Набор
читает `Partners.Balance` и идёт по `CanRequest`:

| `CanRequest` | Что ждёт набор | Итог |
|---|---|---|
| `true` | заявка принята, повтор с другой суммой — `409 IDEMPOTENT_MISMATCH` | зелёный; если дверь отказала `INSUFFICIENT_BALANCE` — красный: врёт `can_request` |
| `false` | заявка отбита `409 INSUFFICIENT_BALANCE` | зелёный, и в журнале теста — «положительная ветка выплаты не измерена: доступно X, порог Y»; если дверь заявку приняла — красный: врёт баланс |

У свежего партнёра песочницы всё в холде, поэтому обычно измеряется вторая
строка. Положительная ветка измерится, когда холд созреет и доступное дорастёт
до порога.

Опции: `PartnerExternalID`, `OfferID`, `ExternalIDPrefix`, `SkipPayouts`.
`SkipPayouts` пропускает цепочку выплат целиком и нужен теперь редко: партнёр без
одобренного баланса набор больше не роняет. Он нужен, только если на площадке
нельзя создавать заявки вовсе.

Прогон против песочницы из этого репозитория:

```sh
RECCA_CPA_SANDBOX_KEY=<ключ арендатора песочницы> go test -run TestConformanceAgainstSandbox -v .
```

Без ключа тест пропускается с объяснением (`SKIP` виден в выводе).

### Сценарии приёмки по договору

Общие цепочки выше проверяют библиотеку и дверь. Сценарии 1–4 дополнения к
Приложению № 1 проверяют свойства конкретных офферов и включаются опцией
`Scenarios` — каждому свой оффер:

```go
cpatest.Conformance(t, client, cpatest.ConformanceOptions{
    Scenarios: &cpatest.ScenarioOptions{
        BrandOfferID: "…", BrandGoal: "brand_registered", // 1: бренды и блогеры
        GoalOfferID:  "…", Goal: "sale",                  // 3: целевое действие
        RevshareOfferID: "…",                             // 2 (скаут) и 4 (revshare)
    },
})
```

Ожидаемые суммы набор выводит из условий оффера у той же двери, а каждый шаг
пишет `request_id` — вывод `go test -v` и есть протокол приёмки. В песочнице
офферы приёмки уже заведены; их идентификаторы передаются вместе с ключом.
⚠ Смену статуса по истечении холда (сценарий 3) набор в том же прогоне не
измеряет: её доказывает вебхук `cpa.conversion.approved`, пришедший после холда.

# Для разработчиков SDK

Источник правды — контракт в репозитории Recca: `docs/federation/cpa-api.md` и
`docs/federation/openapi-cpa.yaml`. ⚠ Там, где описание расходится с кодом
двери, верен код двери (`apps/backend/src/api/federation/v1/cpa/**`).

⚠ **Рантайм и типы пишутся РУКАМИ, а не генерируются.** Прежняя редакция этой
строки обещала генерацию методов из контракта — обещания не исполнял никто, а
читалось оно как описание существующего. Генератора нет; когда он появится,
швом станет граница пакета `cpatypes`, где живут типы контракта и ничего кроме
них. Клиент, транспорт и политика повторов останутся ручными: там принимаются
решения, а не повторяется форма.

| Пакет | Что в нём |
|---|---|
| `go.recca.ru/cpa` | клиент, опции, ошибки, короткие имена типов — один импорт для квикстарта |
| `go.recca.ru/cpa/cpatypes` | типы контракта: деньги, идентификаторы, параметры, коды ошибок |
| `go.recca.ru/cpa/cpatest` | стенд и приёмочный набор `Conformance` |
| `go.recca.ru/cpa/postback` | подпись и проверка ВХОДЯЩЕГО постбэка рекламодателя |
| `go.recca.ru/cpa/webhook` | проверка подписи ИСХОДЯЩЕГО вебхука Recca |
| `go.recca.ru/cpa/internal/transport` | повторы, паузы, разбор конверта, отладка |

Версия Go — **1.24**, версия потребителя. ⚠ Директива ограничивает язык, но не
символы стандартной библиотеки: вызов функции из 1.26 соберётся здесь и упадёт
у него. Поэтому `go vet` обязателен, а окончательное доказательство — сборка
настоящим тулчейном 1.24 (`GOTOOLCHAIN=go1.24.13`).

Проверка: `gofmt -l .` пусто, затем `go build ./... && go vet ./... && go test ./...`

## Мутационный прогон

`go run ./tools/mutate` (или `-run <подстрока имени>`). Каждая мутация снимает
одно решение и обязана уронить тест, который это решение стережёт; красное по
сборке не засчитывается. Каталог — `tools/mutate/catalog.go`, его якоря сверяет
обычный `go test`.

⚠ Мутация — правка исходника, поэтому раннер:

- **не стартует на грязном дереве** — печатает `git status --porcelain` и выходит;
- восстанавливает файл после каждой мутации (`defer`) и по Ctrl-C / SIGTERM;
- перед мутацией пишет журнал в `.git/mutate-journal.json`, и если процесс убит
  жёстко (такое не перехватывается ничем), **следующий запуск возвращает файл
  сам** — но только если файл после обрыва никто не менял; иначе стоп, решает
  человек;
- после прогона проверяет, что дерево снова чистое.

## Векторы и коды ошибок

`testdata/` — копии артефактов контракта, порождённых живым кодом Recca:
подписи постбэка, подписи вебхука, реестр кодов ошибок. Обновляются командой
`pnpm sdk:sync-contract <путь к клону>` из репозитория Recca
(`scripts/sdk-go/sync-contract.mjs`), руками не правятся.

Расхождение с оригиналом красит тесты **здесь**, а не у клиента: ломающая
правка подписи обязана быть видна до того, как её увидит интегратор.
